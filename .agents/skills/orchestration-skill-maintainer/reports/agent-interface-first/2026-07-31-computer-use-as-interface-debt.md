# Computer Use as agent-interface debt

## Observation

The active Orchestrator coaching trace contained 31 Computer Use calls, mostly for launcher discovery, activation, inspection, recovery, and navigation. These were routine product operations performed through the desktop because a quiet semantic route was absent or not selected.

The first skill version also named real desktop behavior as a normal reason to use Computer Use. The user clarified that literal desktop-flow testing is rarely the objective; the priority is efficient, non-obtrusive agent work. Exceptions must remain possible without being advertised as ordinary testing lanes.

## Theory

The first description triggered mainly when Computer Use was already contemplated. Its named exception categories gave agents ready-made reasons to proceed with desktop interaction. Agents optimizing for immediate evidence could therefore treat a rare escape hatch as an expected validation method.

## Revision

Reformulated the complete skill around quiet structured operation. Its description now triggers during setup, navigation, inspection, testing, review preparation, lifecycle control, recovery, or similar work before a desktop-control choice is made.

The body makes semantic background-capable interfaces the default and treats direct desktop interaction as a rare, contextual exception after suitable structured routes are exhausted and the remaining value justifies its intrusion. It provides no catalogue of pre-approved exceptions.

Repeated desktop work becomes agent-interface debt. The agent implements a bounded route when authorized or records and routes it separately while continuing trustworthy work where possible.

## Exposure

All sessions see the general skill's metadata, but full instructions depend on skill loading. Fresh-agent tests showed that metadata influenced general and worker reasoning without reliably demonstrating ingestion; a reviewer selected the skill explicitly.

The detailed principle remains only in `agent-interface-first`. One-line loading boundaries now exist in the active roles that prepare, execute, or accept software interaction:

- general Review Coach;
- ad-hoc Orchestration Worker and Review Before Merge;
- provisional Work Unit and Work Unit Review.

Planning and currently implemented product harness roles were left unchanged because they do not perform this interaction. Future agent-operating product harnesses should make the skill always applicable centrally rather than duplicate it across role definitions.

## Evaluation

The revision strongly favors quiet work without claiming that exceptions are impossible. The loading hooks are limited to roles whose immediate responsibilities can lead to UI operation, so they improve discovery without turning the principle into broad planner policy or repeating its contents.

Fresh worker and reviewer scenarios preferred structured launch, fixture, state, capture, and viewport routes and rejected repetition as justification for desktop control. A deliberately unusual prompt still permitted one bounded action when that exact interaction was the explicit acceptance question, confirming that the formulation leaves contextual exceptions possible without naming ordinary permission categories.

No product code or harness configuration changed.
