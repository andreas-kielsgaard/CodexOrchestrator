# Capability Profile and Worktree Review correction

Status: proposed implementation shape, 2026-09-22. No implementation is authorized by this plan.

## Target and boundaries

After a local Codex profile/harness is registered in Technical Settings, a user can create, edit, save, and reopen a Capability Profile without a working Codex process or provider connection. The profile records intended routes, model/reasoning options, MCP groups, and skill roots. Orchid checks actual execution capability when an Agent Session instance launches, not when the configuration is saved.

At launch, the chosen route and enabled MCP/skill groups determine what that instance receives. This slice does **not** add broad model/reasoning policy enforcement, alter manual Agent Sessions capability pickers, or add remote Orchid Network control. Keep SSH as developer configuration outside Orchid UI. Worktree Review should distinguish existing attached worktrees from detached ones and make build activity/failures inspectable.

## Ownership and sequence

1. Make the registered Device -> Harness -> Inference Source route a non-executing catalogue used by both Technical Settings and Capability Profiles.
2. Make Capability Profile CRUD depend on structural configuration only. Persist the latest successful per-route model catalogue for offline editing; observe live runtime separately.
3. At Agent Session instantiation, resolve the selected route and compile the MCP/skill exposure for that instance. Preserve the established manual session UI behavior.
4. Reshape Worktree Review navigation and the build lifecycle/read model. Prove the resulting flows in the running app.

The stages can be implemented and tested independently, but profile creation is the first acceptance gate. No new library is needed: reuse the existing Native Profile repository, SQLite storage, Tauri commands, Harness Engine broker, Git observation, and build log.

## Capability Profile: configuration, not execution

- **Extract** the local route projection currently implicit in `src/features/technicalSettings/ExecutionSetupOverview.tsx` and `src/features/executionConfiguration/ExecutionConfigurationScreen.tsx` into one pure, discoverable application-layer projection over registered native profiles. Both screens consume the same device/harness/source labels and binding IDs. Registration is enough to offer a route; login, `model/list`, MCP inventory, and executable health are not route-presence tests. An unavailable/deleted registration remains visible on a saved profile as a broken reference, not an empty editor.
- **Adapt** `ExecutionConfigurationScreen.tsx` and `useExecutionConfigurationCatalog.ts`: load profile list/detail, registered routes, and optional OTP metadata independently. Do not use one `Promise.all` in which `loadSelectedRuntimeProfile()` failure suppresses saved profiles or routes. A live observation failure becomes a scoped, non-blocking status near the affected route. An explicit refresh may retry it.
- **Adapt** `CapabilityProfileEditor.tsx`: keep the current route list and group editor, but source route choices from registration. Existing saved selections remain displayed even if absent from the current catalogue. Model choices combine the most recent successful route-specific observation with saved entries; mark a cached observation's time and stale status. If a route has never been observed, allow an empty model list and saving the profile; do not fabricate supported models or block route creation. Keep model/reasoning order and per-model ranges in the editor as design-time intent, not a promise of current availability.
- **Create** a small backend model-catalogue cache (in `src-tauri/src/execution_configuration/` storage and transport) keyed by stable registered configuration reference, with observed time and only non-secret model/reasoning descriptors. Replace an entry only after a successful complete model observation. A failed probe must not erase the last good entry. Avoid caching login secrets or the entire mutable runtime response. If this configuration has never been observed, return an explicit `unobserved` state.
- **Adapt** `src-tauri/src/execution_configuration/service.rs`: remove `runtime_for_binding`/`describe_runtime` calls from profile create and update. Validate name, IDs, unique route/model entries, default route membership, and syntactic reasoning range; do not compare entries with a live catalogue or flattened `allowed_capabilities` on every route. Generate the profile ID on first save as today. Keep the legacy persisted fields needed to read existing profiles/session snapshots, but stop treating their cross-route union as a runtime authority. Put any route-reference warning in the read model rather than making old profiles unreadable.
- **Retain** explicit Codex health/login/inventory operations in Technical Settings. Their failures are diagnostics, not profile CRUD failures. Remove editor copy implying that a successful save verifies executable/provider capability.

## Agent Session instance: selected exposure

- **Adapt** `src-tauri/src/agent_sessions/application/configuration.rs`, `preparation/execution.rs`, and the workflow session-creation path so a profiled session uses its pinned default/selected route, not a global selected Codex home. Resolve that route against actual runtime at instance launch. Fail with an actionable route-specific error there if the executable, login, provider, or required exposure cannot be materialized. A saved profile remains intact.
- **Retain** direct-user model and reasoning selection semantics already present. Do not add a Capability Profile range gate to manual sends or workflow dispatch in this slice. The model list/range stored on the profile is configuration intent for later policy work; the launched runtime still must accept the actual requested model and reasoning. Do not claim enforcement in UI copy.
- **Adapt** `src-tauri/src/execution_configuration/session_skills.rs` to compile the selected route's enabled roots, not always `default_route()`. Only advertise an OTP skill group if its registration actually supplies a skill root; `src-tauri/src/otp_api/contract.rs` and the TS contract may need a minimal root descriptor. Preserve source fingerprints and recheck them before use.
- **Adapt** group-to-MCP materialization at launch. Map enabled Orchid/OTP groups to canonical tools in the existing per-session Harness Engine broker exposure; do not create child sidecars. Native Codex-configured MCPs are enabled/disabled only at server/group level through ephemeral launch configuration, without writing `config.toml` or accepting arbitrary overrides from the frontend. Do not claim per-tool enforcement for native servers.
- **Replace the skill delivery assumption:** `crates/orchid-engine/src/codex/app_server/mod.rs` currently attaches every selected `skill` input to every turn, while the documented app-server input is for explicit invocation. Do not force-invoke the entire allowed set. Extend the existing product-owned `RuntimeLaunchExtension`/prompt-prefix path to present the pinned manifest's selected skill names/descriptions on each turn, with an on-demand, manifest-authorized skill reader through the existing broker. Keep that text distinct from the user's submitted message in Orchid's records. Reuse pinned source paths/fingerprints; do not add a second skill root or copy files. Live-test the installed app-server and confirm the runtime does not present disabled roots as Orchid-approved skills; document any Codex-native visibility that cannot be masked.
- **Retain** pinned session exposure for existing sessions; profile edits affect only new instances. Avoid a new general policy framework or broad Agent Sessions UI changes.

## Worktree Review: navigation and usefulness

- **Adapt** `WorktreeSelector.tsx`: list matching associated worktrees first, then place a button labelled **Create new worktree** below them. Explain “Checkouts requiring association” as existing Git checkouts reachable from the selected branch but not yet explicitly associated with that branch in Worktree Review; they are not necessarily newly created or necessarily detached HEAD. Prefer a concise label such as **Other existing checkouts** with the association reason and action, leaving the domain distinction intact.
- **Extract** Worktree Review-specific navigation from `BranchNavigator.tsx` rather than changing the shared `BranchBrowser.tsx` used by Agent Sessions. Filter detached-HEAD worktree targets out of the Branches count/list, and add a separate **Detached worktrees** count and **View details** action below Branches. Selecting it shows a right-pane list, not a destructive cleanup action.
- **Adapt** the `worktree_review` inventory/detail read model (`branch_inventory.rs`, `branch_first.rs`, `branch_presentation.rs`) for that list. Show path, HEAD, dirty state and counts, approximate last activity, recorded association/last known branch if Orchid actually has it, and current session/build references if available. Creation date is shown only if Orchid recorded it; Git does not guarantee it. Calculate disk size only when details are opened, label it approximate, and never follow symlinks outside the worktree. Show `Unknown` rather than infer historical metadata from a current commit. Reuse `worktree_activity.rs` and existing Git status observation.
- **Retain** current association and build behavior for attached worktrees. Do not add deletion controls to the new detached view in this slice; the details help a user decide what to inspect next.

## Build progress and useful failure output

- **Adapt** `src-tauri/src/worktree_review/build_service.rs` and `transport.rs` so starting a build returns its persisted build/attempt identity promptly; work continues in a task whose stage, timestamps, and terminal result can be read later. The UI polls while visible and can reattach after tab switch/restart. Stage names come from the real materialization, TypeScript, frontend, Cargo/Tauri, and publication steps; display elapsed time. Only show a remaining-time estimate if measured evidence supports it, otherwise say it is unknown.
- **Create** a bounded read-only log endpoint resolving an attempt ID through the Worktree Review repository to its retained `build.log`. Return incremental chunks/offset and a terminal stderr excerpt; never accept a caller-supplied path. Adapt `BuildHistory.tsx` and `WorktreeReviewScreen.tsx` to show a live stage/log pane and actionable terminal summary instead of only `node.exe failed (1)`. Keep a link from retained result to the full log when present.
- **Adapt** `scripts/build/application.mjs`/`process.mjs` to emit parseable stage markers alongside ordinary tool output and preserve the final failure context. Do not hide Cargo's actual error behind a generic process-exit message. Reuse the existing log redirect and cache layout rather than introducing another build runner.
- **Adapt** `scripts/build/cargo.mjs` target selection for Worktree Review builds: when its prospective output binary is the currently running Orchid executable, choose a review-owned build target for that checkout instead of asking Cargo to replace the live executable. Keep its cache across builds. For other locked files, report the exact failing path and recovery action; do not kill running processes or clear broad caches.

## Verification and acceptance

- Backend tests: profile CRUD with malformed/unavailable Codex config, multiple registered routes, missing and stale model cache, failed refresh retaining last good cache, saved-profile reopen, structural invalid data, selected-route instantiation, managed MCP mask, native MCP group override, and selected skill-root/OTP materialization. Explicitly test that model/reasoning ranges do not become new policy gates.
- Frontend tests: registered route appears despite runtime error; create/save/reopen a profile; cached/unobserved model states; disabled/deleted references shown; attached and detached worktree navigation/counts; create button placement; build stage/log/failure views and reattachment.
- Live app flow: register/use the existing local Codex harness, create and edit a profile while runtime observation fails, restart and reopen it, then try session launch and see the failure at the correct boundary. After fixing the runtime separately, launch once and inspect actual MCP/skill exposure. Build from the running app, watch the log through completion/failure, and inspect detached worktree details. Record any protocol limits found rather than claiming unproven enforcement.

## Explicit non-goals

No model/reasoning enforcement expansion; no global manual-session UI restriction; no sandbox setup; no SSH product settings; no Orchid Network implementation; no per-session MCP sidecar; no deletion/cleanup UX for detached worktrees; no synthetic ETA or guessed Git provenance.
