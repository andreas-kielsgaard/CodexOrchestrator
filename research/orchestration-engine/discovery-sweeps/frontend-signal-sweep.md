# Signal sweep: frontend behavior

Snapshot: research checkout `924036424969de293da17d0e29c67c34d1ec7c81`.

This is an evidence ledger of frontend-visible and frontend-triggerable behavior. It deliberately does not group signals into proposed product capabilities and does not recommend keeping or removing anything. "Boundary" means the first application client, adapter, browser API, or local state boundary reached from the signal; it is not a claim about the full backend effect.

Static reachability was checked from the actual HTML/TypeScript entry points and imports, excluding test-only imports. A command existing in the Tauri handler is recorded separately from a control that can initiate it.

## Boundary notes for later sweeps

- The normal frontend is primarily query-driven: orchestration projection, planning drafts, proposals, transitions, harness inspection, Agent Session details, and native profile cards all re-read authoritative state rather than projecting success from command acknowledgment.
- The frontend still contains materially different operational families at the same build boundary: current product composition, recorded URL compositions, a separately built recorded harness, debug-only Human Review controls, retained-instance chrome, and unmounted Task Dashboard/runtime-exploration artifacts.
- Several apparent controls are deliberately negative-capability signals: artifact access and automatic-flow mutations produce explicit unsupported feedback; product Harness Management exposes inspection without dispatch; embedded orchestration Sessions are read-only unless writability is explicitly supplied.
- Periodic activity is concentrated in active Agent Session fallback polling and Human Review proof/progress navigation. Normal orchestration and proposal state do not poll; they rely on mount/workflow refreshes plus Agent Session and initiation events.
