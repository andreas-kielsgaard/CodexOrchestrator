# Signal sweep: agent, process, MCP, CLI, environment, and executable configuration

## Inspection boundary

This is a source-led inventory at research checkout commit `924036424969de293da17d0e29c67c34d1ec7c81`. It records observable triggers and effects without first grouping them into product capabilities. A row can therefore expose a product path, an internal transition, an operator utility, a debug seam, a quarantined predecessor, or a test seam. Presence in source is not treated as proof of product reachability.

The dimensions are deliberately behavioral:

- **Trigger**: what initiates the signal.
- **Authority/effect**: what the code is allowed to decide, launch, mutate, or expose.
- **Result/receipt**: what evidence actually comes back; absent evidence is called out.
- **Reachability**: whether the current application composition can reach it.
- **Artifacts**: exact source locations and principal symbols.

Reachability labels used below are `productive`, `productive/internal`, `debug-only`, `operator CLI`, `quarantined`, `source-present/unreached`, and `test-only`.

## Cross-signal observations

These are provisional architectural observations from the ledger, not keep/tune/prune decisions.

1. **Configuration is part of the execution authority chain.** `conversation_harness_catalog.json`, immutable Harness revisions, MCP `-c` arguments plus bearer-token environment entries, native-profile readiness/binding records, selected execution mode, debug-enabling environment variables, and the application source checkout's Git state all determine what can launch and what it may change.

2. **There is no single process-launch policy.** The generic Agent Session adapter inherits the parent environment and owns only a direct child. Native-profile operational children clear and rebuild the environment but still own only a direct child. The debug review runtime clears/project-isolates most child environments and uses a Windows Job Object for descendant ownership.

3. **MCP transport code is repeated.** Plan Builder, bootstrap, the Sprint-family macro servers, the special Epic Runner server, and native-profile reporting each implement variants of loopback bind, bearer/Host/Origin enforcement, rmcp serving, cancellation, and stop/join. Tool effects are distinct; the transport lifecycle is substantially parallel.

4. **The effective Harness is layered.** Static role JSON supplies baseline prompt/skill/runtime/MCP declarations. Immutable revision bridges specialize Handler and Implementer stages. Transition code then adds per-invocation MCP arguments, bearer environment, working directory, and application-authored instruction text. No one artifact is the complete launch contract.

5. **Git has multiple trust/environment policies.** File-review reads use a strongly isolated Git subprocess. Accepted integration narrows Git configuration but inherits more environment. Execution-workspace creation and Sprint authority checks inherit still more user/system Git context. These differences affect reproducibility and authority analysis.

6. **Repository state is productive configuration.** The current clean application source checkout, its `HEAD^1`/`HEAD`, compile-time manifest-derived root, and on-disk product skills are consulted by productive orchestration. They are not merely build inputs.

7. **Several parallel or residual surfaces remain visible.** Rust and Node worktree runtimes overlap; legacy Task UI/client/local composition remains beside universally quarantined backend commands; generic native `project_launch` is largely unused; direct Harness editing methods lack a current transport; debug/operator inspection tools are numerous but intentionally outside the product invoke surface.

8. **Receipts are generally more precise than process outcomes.** Productive orchestration tools frequently distinguish request, launch acceptance, provider activity, lifecycle, semantic completion, review acceptance, integration, and settlement. The places most likely to confuse those boundaries are operator scripts and old/quarantined runtime seams rather than the newer orchestration transitions.
