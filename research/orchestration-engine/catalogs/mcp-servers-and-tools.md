# MCP servers and agent-facing tools

## Product role

MCP is the principal mutation surface for managed orchestration agents after the frontend has initiated or displayed a workflow. These tools are not Tauri endpoints and they are not available to arbitrary Agent Sessions. The application creates a transient server for an exact invocation, injects only its allowed tools into that Codex child, revalidates durable authority in every tool handler, and stops the server after terminal observation or shutdown.

The current inspected line implements 14 semantic server variants exposing 23 distinct tool names.

## Endpoint definition model

There is no central MCP endpoint-definition file. Tool schemas are generated by `rmcp` and `schemars` from Rust parameter structs and `#[tool]` declarations located alongside the service logic. Human-readable policy is further distributed across:

- tool descriptions;
- MCP server instructions;
- Harness prompt prefixes;
- product skill text;
- application-generated continuation prompts;
- enabled-tool lists in Harness configuration and injection code.

Consequently, the table above is a derived catalogue rather than a view over one authoritative registry.

## Shared orchestration transport

All orchestration servers follow the same operational pattern:

- bind `127.0.0.1` on an ephemeral port;
- expose `/mcp` over HTTP/1;
- run a current-thread Tokio runtime inside an owned standard thread;
- use rmcp Streamable HTTP with in-memory sessions;
- generate a random bearer token and child-only environment variable;
- retain the server handle under the exact invocation ID;
- stop it after terminal reconciliation or service shutdown.

`CodexMcpInjection::new_named` in `orchestration/mcp.rs` builds dynamic Codex configuration for:

- URL;
- bearer-token environment-variable name;
- enabled tools;
- required-server behavior;
- automatic tool approval;
- ten-second startup timeout;
- 300-second tool timeout.

The bearer value is passed through `CODEX_ORCHESTRATOR_MCP_<uuid>`, not embedded in the command-line configuration.

### Transport guard

The shared orchestration guard requires:

- exact `Authorization: Bearer ...`;
- exact loopback `Host`;
- if present, `Origin: tauri://localhost`.

An absent Origin is accepted. The loopback/transient design uses the random bearer as its primary caller secret rather than TLS.

## Durable authority behind transport authority

Possessing the bearer token is not sufficient to perform an arbitrary orchestration mutation. Tool inputs omit most identities deliberately. A server is bound to an invocation ID, and the called service revalidates the corresponding durable facts, including combinations of:

- role and lifecycle stage;
- Session and invocation correlation;
- Harness revision/digest/local commit reference;
- current proposal or planning revision;
- Epic, Sprint, planning point, Work Unit or attempt authority;
- expected delivery or routing state;
- idempotency and replay fingerprint.

This is an important product boundary: MCP is a capability transport, while the database remains the semantic authority.

## Behavioral differences and inconsistencies

### Tool result semantics

Many Sprint/execution tools return a protocol-successful `CallToolResult` containing a rejected application outcome such as `forbidden`, `conflict` or `unavailable`. Plan Builder tools use MCP error results for several comparable failures. A future shared endpoint layer would need to preserve or deliberately normalize this difference.

### Human initiation wait

`request_epic_initiation` can wait up to 240 seconds for explicit frontend confirmation. The agent request, user decision and durable initiation remain separate stages.

### WorkspaceWrite reporting exception

The Implementer reporting continuation adds:

- `sandbox_workspace_write.network_access=true`;
- `features.network_proxy=true`.

The code checks the complete expected injection shape before launch. This exception exists because the relevant Codex CLI version needs network access for loopback MCP from WorkspaceWrite. The requested configuration is nevertheless broader than a typed “loopback only” capability, making it a security/configuration seam worth revisiting.

## Native-profile MCP divergence

`native_profiles.rs` independently implements its listener, transport guard, Codex injection, process dispatch and receipt settlement rather than reusing `CodexMcpInjection`.

The probe launches `codex exec` with strict application-owned configuration, ignored user config/rules, WorkspaceWrite sandbox and a dedicated probe root. It manually installs the fixed reporting server and instructs the agent to call only `report_native_profile_readiness`.

Differences from orchestration hosting include:

- a separate bearer environment-variable family;
- bearer and Host checks but no Origin rule;
- a durable pending/dispatching/received probe lifecycle;
- receipt correlation evaluated separately from process exit;
- no shared invocation-server registry.

The initial `b28137b` anchor had a profile-selection race between the first selected-profile check and durable probe insertion. Commits ending at `dbe321d`, now ancestors of the current research tip, add an operation gate and revalidate selection while gated. `9240364` reuses the readiness gate for Agent Session profile binding but does not reuse the native MCP listener or transport implementation.

## Static Harness catalogue coverage

The compiled catalogue declares 14 orchestration tools, not all 22 orchestration tools in the runtime catalogue. Eight stage-specific tools are introduced through Rust-authored/durable Harness revisions:

- `report_pre_start_outcome`;
- `start_selected_sprint`;
- `record_started_reevaluation`;
- both Implementer reporting tools;
- all three Handler review tools.

The static role profile is therefore a base configuration, not an exhaustive endpoint registry. For example, the static Sprint Runner profile has no required MCP tools while runtime continuations inject required pre-start and started endpoints.

## Architecture candidates

- central role/stage/tool registry that can generate Harness declarations, injection allowlists and inspection data;
- shared listener, guard, lifecycle registry and shutdown infrastructure;
- uniform application-outcome/error contract;
- explicit configuration type for loopback MCP access from WorkspaceWrite;
- shared transport policy for orchestration and native-profile servers;
- tool catalogue exposed to Harness inspection from actual pinned durable revisions.

Any centralization should preserve invocation-bound semantic authorization rather than reducing it to a global tool server.
